# Sprint 2 — User Stories and Subtasks

Sprint 2 focused on building the carrier integration layer and the core API. The work is organized into two weeks with distinct objectives.

## Week 1: Data model, state mapping, and order endpoints

**Observed dates:** 29 September to 5 October 2026

| Story | Jira | Title | Epic | Status |
|---|---|---|---|---|
| HU-11 | RIWI-52 | Implement the Complete WMS ORM Model | Data Model & Persistence | Merged to `develop` |
| HU-12 | RIWI-57 | Create the Configurable State Mapping Model | Data Model & Persistence | Merged to `develop` |
| HU-13 | RIWI-63 | Order CRUD Endpoints | Core Endpoints | Merged to `develop` |

### HU-11 — Implement the Complete WMS ORM Model

**Goal:** Create the SQLAlchemy models and initial Alembic migration for the 12 operational tables.

| Subtask | Jira | Work |
|---|---|---|
| Create Order model | RIWI-53 | `brand_id`, `dc_id`, `created_at`, `dispatched_at`, `status` |
| Create Shipping Label model | RIWI-54 | 1 order → N shipping labels (RN-07) |
| Create Carrier Event model | RIWI-55 | Raw status + canonical status + timestamp |
| Generate and apply initial migration | RIWI-56 | Alembic `upgrade head` |

### HU-12 — Configurable State Mapping

**Goal:** Translate each carrier's status into canonical states, with mapping changeable without restart (CA-06).

| Subtask | Jira | Work |
|---|---|---|
| `StateMapping` model | RIWI-58 | `carrier_id`, `raw_status`, `canonical_status` |
| Initial seed for simulated carriers | RIWI-59 | ≥6 distinct source statuses per carrier |
| In-memory cache with invalidation | RIWI-60 | 300s TTL, invalidated on write |

**Result:** `state_mapping` table with `UNIQUE(carrier_id, raw_status)` and `CHECK` constraint on canonical status. Admin API at `/api/v1/admin/state-mappings`. Migrations `a3f1c9d27b45`, `b7e24d51c8a9`, `c4a1209b7e6f`.

### HU-13 — Order CRUD Endpoints

**Goal:** Expose the basic order life cycle through the API.

| Subtask | Jira | Work |
|---|---|---|
| `POST /api/v1/orders` | RIWI-64 | Create order with lines and recipient |
| `GET /api/v1/orders` and `GET /api/v1/orders/{id}` | RIWI-65 | Paginated listing and detail |
| `PATCH /api/v1/orders/{id}/status` | RIWI-66 | Status update with RN-02 terminal state protection |
| pytest tests | RIWI-67 | Integration tests against real database schema |

### HU-17 — Webhook Simulator (5 Type A Carriers)

Generates events across 5 heterogeneous formats: Flat JSON (`alpha`), Nested JSON with numeric codes (`beta`), Spanish JSON (`gamma`), XML (`delta`), and URL-encoded form (`epsilon`).

### HU-20 — Webhook Ingestion & RN-02 Protection

**Goal:** Connect webhook receivers to canonical normalization and strictly prevent reverting terminal states.

| Subtask | Jira | Work |
|---|---|---|
| Format decoders | RIWI-95 | Decoders for all 5 Type A carrier formats |
| Normalization service | RIWI-96 | Translate raw status to canonical status using cached mapping |
| RN-02 terminal state protection | RIWI-97 | Reject reverting `DELIVERED`, `RETURNED`, or `LOST_OR_DAMAGED` |
| Tracking anomaly logging | RIWI-98 | Save invalid transitions and unknown tracking numbers to `tracking_anomalies` |
| RN-07 order propagation | RIWI-99 | Mark parent `Order` as `DELIVERED` only if all shipping labels are delivered |

### HU-21 — Type B Carrier REST API Connector

**Goal:** Pull tracking events from external carrier REST APIs by tracking number with resilience.

| Subtask | Jira | Work |
|---|---|---|
| `TypeBConnectorService` | RIWI-102 | HTTP client querying `GET /shipments/{tracking_number}` |
| Exponential backoff | RIWI-103 | Retry mechanism with jitter on HTTP `429 Too Many Requests` and `5xx` |
| Canonical normalization | RIWI-104 | Reuses `NormalizationService` (RN-01, RN-02) and timestamps parsing |
| Sync endpoints | RIWI-105 | `POST /api/v1/type-b/sync/{carrier_id}` and bulk sync endpoint |

### HU-22 — Type C Batch File Connector

**Goal:** Ingest CSV and Excel files from Type C carriers, cleaning known data quality defects and deduplicating.

| Subtask | Jira | Work |
|---|---|---|
| File ingestion endpoint | RIWI-106 | `POST /api/v1/type-c/upload` accepting `.csv` and `.xlsx` |
| Defect 5.3 cleaning | RIWI-107 | Automatically strip total/summary footer rows and repeated headers mid-batch |
| Idempotency & SHA-256 | RIWI-108 | Prevent duplicate ingestion by tracking file hashes in `processed_files` |
| Event normalization | RIWI-109 | Normalize rows and apply RN-02 terminal protection |

### HU-23 — RabbitMQ Webhook Ingestion Decoupling (RNF-01)

**Goal:** Decouple incoming webhooks by publishing to RabbitMQ instead of synchronous processing, satisfying the RNF-01 SLA.

| Subtask | Jira | Work |
|---|---|---|
| RabbitMQ setup | RIWI-111 | RabbitMQ service in `docker-compose.yml` (`5672` AMQP, `15672` UI) |
| Topology design | RIWI-112 | `eventos_exchange` (Topic), `eventos_transportadora`, `retry` with TTL, and `dlq` |
| Webhook publisher | RIWI-113 | Ingest endpoint returns `HTTP 202 Accepted` (`status: "queued"`) in < 20 ms |
| p95 latency benchmark | RIWI-114 | 100 concurrent requests measured: **p95 = 32.60 ms** (Target: < 200 ms) |

### HU-24 — Standalone Consumer Worker with ACK/NACK

**Goal:** Independent background worker process consuming queue messages and applying normalization with ACK/NACK.

| Subtask | Jira | Work |
|---|---|---|
| Worker process | RIWI-116 | Standalone process `app/worker.py` with OS signal handling |
| ACK/NACK mechanics | RIWI-117 | Send ACK only on success; forward to retry queue on transient failure; send NACK to DLQ on exhausted retries |
| Docker service | RIWI-118 | Containerized `worker` service added to `docker-compose.yml` |
| Verification tests | RIWI-119 | Unit tests for ACK/NACK and E2E eventual normalization test |
