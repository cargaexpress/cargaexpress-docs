# Carrier Data Ingestion

The target architecture considers three integration patterns. The appropriate pattern is selected per carrier contract, not assumed to be the same for every carrier.

## Push integration

A carrier sends shipment events to a CargaExpress endpoint. The receiver should validate the payload, identify the source, retain the original event, and acknowledge or reject the request according to the contract. Authentication, retry, and signature requirements must be defined per carrier.

## Pull integration

CargaExpress queries a carrier endpoint for shipment information. The known Type B API contract uses an individual tracking-number query:

```http
GET /shipments/{tracking_number}
```

The pull process must respect each carrier's request limits and schedule. The Type B simulator requirements discussed a 30-minute cadence/limit, configurable rate limiting, and testable error scenarios. Confirm exact production polling and rate-limit semantics in the approved API contract.

## File-based integration

A carrier or partner provides a batch file. The import process should validate the file format, required fields, timestamp formats, source identity, duplicates, and row-level errors. Invalid rows must be visible for correction rather than silently discarded.

## Common processing pipeline

1. Identify the carrier and integration contract.
2. Receive or fetch the source payload.
3. Persist or log the original payload for traceability.
4. Validate required fields and parse timestamps.
5. Map source status to the canonical state catalog.
6. Apply transition and ordering rules.
7. Update the shipment projection without losing event history.
8. Expose failures, unknown states, and anomalous events for review.

## Implementation status

All three ingestion patterns and their canonical processing pipelines are fully implemented, tested, and containerized in the CargaExpress Control Tower:

1. **Push Integration (Type A Webhooks — HU-20 & HU-23)**:
   - Receives events in 5 distinct formats (flat JSON, nested JSON with numeric codes, Spanish JSON, XML, and URL-encoded form).
   - Ingests asynchronously via RabbitMQ topic exchange (`eventos_exchange`) satisfying **RNF-01** (p95 = 32.60 ms &le; 200 ms).
   - Dispatches to consumer workers (`app.worker`) for canonical normalization, RN-02 terminal state protection, and PostgreSQL persistence.

2. **Pull Integration (Type B REST APIs — HU-21)**:
   - Queries `GET /shipments/{tracking_number}` via `TypeBConnectorService` (orchestrated periodically via Apache Airflow `dag_type_b_polling.py`).
   - Incorporates exponential backoff with jitter on HTTP `429 Too Many Requests` and `5xx` server responses.
   - Parses heterogeneous ISO 8601 timestamps and synchronizes state into canonical models.

3. **Batch File Integration (Type C Files — HU-22)**:
   - Ingests CSV and Excel (.xlsx) files via `TypeCConnectorService` (scheduled via Apache Airflow `dag_type_c_ingestion.py`).
   - Strips Defect 5.3 data quality flaws (summary/total footer rows and repeated mid-file header lines).
   - Enforces ingestion idempotency via SHA-256 file hashing tracked in `processed_files`.
