# Business Rules: RN-01 to RN-10

The project defines ten business rules. Their content has been reconstructed from the code, seed data, architecture decisions, and documentation across all project repositories.

## RN-01 — Canonical shipment-state catalog

The system uses exactly 8 canonical states. All carrier-specific statuses must be mapped to one of these values using the `state_mapping` table. No other canonical values are allowed.

**States:** `CREATED`, `PICKED_UP`, `IN_TRANSIT`, `OUT_FOR_DELIVERY`, `EXCEPTION`, `DELIVERED`, `RETURNED`, `LOST_OR_DAMAGED`.

**Implementation:** `StateMapping` model with a `CHECK` constraint in PostgreSQL. Admin API at `/api/v1/admin/state-mappings`. See [Canonical Shipment States](./canonical-states.mdx).

## RN-02 — State transition rules and final-state protection

Terminal states — `DELIVERED`, `RETURNED`, and `LOST_OR_DAMAGED` — are **irreversible**. Any carrier event that attempts to transition a shipment backward from a terminal state must be:

1. Recorded in the raw event log for traceability.
2. Rejected at the normalization layer — the canonical status must not be updated.
3. Flagged as an anomaly for operational review.

**Implementation status:** The rule is defined and documented. The `PATCH /orders/{id}/status` endpoint currently performs **direct** status updates without checking for terminal state regression. Full enforcement is pending.

**Test scenario:** `SCN-07` creates an event arriving after `DELIVERED` to validate this rule.

## RN-03 — SLA calculation in business days

The SLA is measured in **business days**, excluding Sundays and public holidays of the **destination** country. A **16:00 cut-off** determines when the business day count begins:

- An order dispatched **before 16:00** starts counting on the same day.
- An order dispatched **after 16:00** starts counting on the next business day.

If the distribution center and the destination are in different countries, the clock uses the **destination calendar** (ADR-0010).

**Test scenario:** `SCN-02` tests the Friday 17:00 dispatch with a Monday holiday. `SCN-12` tests cross-country calendar usage (DC in Mexico, destination Peru).

## RN-04 — At-risk order detection

An order is classified as **at risk** when either condition is met:

- **24 business hours or less** remain before the SLA deadline and the order is **not** out for delivery.
- An `EXCEPTION` has been **open for more than 12 hours**.

**Test scenarios:** `SCN-08` (14 business hours remaining, still in transit = at risk), `SCN-09` (same dates but already out for delivery = not at risk), `SCN-10` (exception open for 16 hours = at risk).

## RN-05 — Responsibility and delay attribution

| Stage | Responsible |
|---|---|
| Creation to dispatch | Distribution center |
| Dispatch to delivery | Carrier |
| Issue caused by wrong address | Brand (no penalty) |
| Issue with any other cause | Carrier |

**Delay** = delivery date − SLA deadline. Penalty tiers: 1–2 days late → 5%, 3–5 days late → 10%, 6+ days late → 20% (test defaults from seed data).

**Test scenarios:** `SCN-03` (carrier late), `SCN-04` (DC responsible, 54-hour dispatch), `SCN-05` (brand responsible, wrong address).

## RN-06 — Raw event immutability and traceability

Every incoming carrier event is stored **unchanged** in the raw event store with its original payload, a receiving timestamp, and a **hash** for deduplication. The hash is unique, so identical repeated messages cannot be stored twice. The raw event is **immutable** and partitioned by month (ADR-0007).

## RN-07 — Order-to-label cardinality

One order may have **multiple shipping labels** (e.g., multi-package shipments or relabeling after an exception). An order meets the SLA only if **every** shipping label is delivered on time. One late label makes the whole order non-compliant.

**Implementation:** One-to-many `ORDER → SHIPPING_LABEL` relationship in the schema.

**Test scenario:** `SCN-06` creates an order with 2 labels, one on time and one late.

## RN-08 — Carrier and brand catalog integrity

The carrier catalog and brand catalog must remain consistent. Invalid or orphaned references must be prevented. Foreign-key constraints enforce referential integrity for all relationships in the data model.

**Implementation:** Foreign keys on all model relationships. `POST /api/v1/orders` validates that the brand, distribution center, and shipment type exist before creating the order.

## RN-09 — Carrier compliance monitoring

A carrier that falls below **85% on-time compliance** for two consecutive half-month periods is placed `UNDER_REVIEW`. A carrier with only one bad period remains `ACTIVO`.

**Test scenario:** Carrier 12 in the seed data stays under 85% for two consecutive half-months and is `UNDER_REVIEW`. Carrier 11 has only one bad period and stays `ACTIVO`.

## RN-10 — Seed data reproducibility and idempotency

Seed data must use a **fixed seed value** and be **reproducible** (same seed → same data) and **idempotent** (running twice does not create duplicates). Configurable data quality defects (mixed dates, out-of-order events, duplicates, invalid tracking numbers) must be deterministic and clearly marked.

**Implementation:** Seed scripts use `ON CONFLICT DO NOTHING`, fixed timestamps, and per-order random generators.

## Cross-cutting rules confirmed in project discussions

- Support natural business keys and global identifiers to correlate entities across systems.
- Carrier events may arrive out of order and may use different date formats.
- Carrier-specific state catalogs must be explicitly and versionally mapped to the canonical catalog.
- Unknown carrier statuses must be surfaced for review, never silently misclassified.
