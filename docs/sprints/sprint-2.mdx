# Sprint 2 — Carrier Simulators, APIs, and Data Integration Foundations

## Sprint overview

Sprint 2 focused on preparing the carrier integration layer for CargaExpress Supply Chain. The work established the foundations for interacting with heterogeneous carrier systems, retrieving shipment information, testing different API responses, and preparing external data for future normalization and ingestion into the Control Tower.

The main technical challenge was that carriers do not necessarily share the same API contracts, database technologies, status catalogs, date formats, or event behavior. The simulator layer provides a controlled environment in which these differences can be tested before implementing the complete integration pipeline.

This documentation distinguishes implementation work from requirements and future integration tasks. Features are not considered complete solely because they appear in the backlog or in the simulator contract.

## Sprint objectives

- Prepare independent carrier simulators for integration testing.
- Support shipment lookups using tracking numbers.
- Represent differences between carrier status catalogs and response formats.
- Use heterogeneous database technologies to simulate different carrier environments.
- Support configurable scenarios for testing API errors and unavailable shipments.
- Define repeatable test data and seed requirements.
- Prepare the technical foundation for future data ingestion and canonical status mapping.

## 1. Carrier simulator architecture

The simulator layer isolates carrier-specific behavior from the central Control Tower.

Each simulator represents an external integration boundary. This allows the team to test different API contracts, response formats, data stores, and failure scenarios without depending on live carrier systems.

### Type A — Carrier status variations

The project includes carrier simulation scenarios in which status values differ across providers:

- SimCarrier Alpha reports statuses in English.
- SimCarrier Beta reports numeric status codes.
- SimCarrier Gamma reports statuses in Spanish.
(this have mistakes)

These variations illustrate why the Control Tower must eventually translate external status values into a shared canonical shipment state model.

The canonical state catalog and transition rules are defined separately in the business requirements. The simulators should preserve the original carrier values rather than silently treating different external values as equivalent.

### Type B — REST API pull simulators

Type B represents carrier systems that expose shipment information through REST APIs. The Control Tower is expected to retrieve shipment information by tracking number.

The four independent services use different database technologies:

| Service | Database technology |
|---|---|
| `carrier_a` | PostgreSQL |
| `carrier_b` | MySQL |
| `carrier_c` | MongoDB |
| `carrier_d` | SQLite |

This design provides an integration test environment for systems with different persistence models. It does not mean that the Control Tower itself must use all four database technologies.

The final running configuration, database initialization, and service health must be checked against the current Docker Compose configuration.

## 2. Shipment lookup API

The Type B contract uses an individual shipment lookup endpoint:

`GET /shipments/{tracking_number}`

The endpoint identifies the requested shipment using its tracking number and returns the corresponding carrier data according to the simulator's contract.

Example requests used for scenario testing include:

```http
GET /shipments/RX-83921?scenario=server_error
GET /shipments/TR-2001?scenario=unavailable
GET /shipments/PK-3001?scenario=not_found
GET /shipments/NO-EXISTE
```

The examples represent different test cases:

| Scenario | Purpose |
|---|---|
| `server_error` | Exercise server-error handling. |
| `unavailable` | Exercise service-unavailability handling. |
| `not_found` | Exercise missing-shipment handling. |
| Unknown tracking number | Verify behavior when the requested shipment does not exist. |

These are example requests, not a guarantee that every service currently implements identical scenario behavior. The actual HTTP status codes, response bodies, and supported query parameters must be verified against each service's implementation.

### Expected API behavior

- Identify shipments by their tracking numbers.
- Return data according to the relevant carrier contract.
- Make failure scenarios available for integration testing.
- Apply the agreed request-rate restrictions.
- Document response formats and error behavior.
- Avoid exposing carrier-specific assumptions as universal Control Tower rules.

## 3. Heterogeneous data and integration challenges

The simulators provide a controlled way to reproduce differences that commonly complicate multi-carrier integrations.

### Status catalogs

Carriers can report different status names or numeric codes for similar operational events. The Control Tower must eventually map these values to the agreed canonical states.

### Date and timestamp formats

Carrier responses may use different date formats and timestamp conventions. The ingestion layer will need to parse and validate these values before using them for shipment history, event ordering, or SLA calculations.

### Event ordering

External systems may provide delayed or out-of-order updates. The future ingestion process must distinguish event time from retrieval time and apply the approved transition rules without incorrectly overwriting final shipment states.

### Identity and tracking numbers

Tracking numbers identify shipments within carrier systems. The integration architecture must also account for the project's agreed natural keys and global identifiers so that carrier-specific identifiers can be associated with the correct internal shipment records.

The simulators provide a foundation for testing these differences; the complete normalization and identity-resolution workflow belongs to the Control Tower integration layer.

## 4. Rate limiting and scheduled polling

The Type B integration requirements specify a polling restriction of one request every 30 minutes for each carrier integration.

This restriction is intended to control request frequency and provide a predictable integration schedule. Its exact enforcement scope must be defined in the approved contract: per shipment, per service, per client, or another agreed unit.

The polling interval is an integration requirement, not proof that a complete production ingestion scheduler is already running.

The future orchestration process must account for:

- The agreed polling interval and request limits.
- Retry behavior and temporary service failures.
- Request timeouts and unavailable carriers.
- Duplicate retrievals and idempotent processing.
- Logging and observability of unsuccessful requests.

## 5. Seed data and reproducible testing

The simulator environment requires controlled datasets so that integration tests can be repeated consistently.

The seed-data requirements include:

- Fixed seed data for reproducible scenarios.
- Versioned seed scripts.
- Idempotent execution, so rerunning a seed does not create unintended duplicates.
- Representative shipment tracking numbers.
- Carrier-specific status values and date formats.
- Data suitable for testing successful lookups, missing shipments, and error scenarios.

Seed scripts and their execution procedures must be verified against the current repository. The presence of example tracking numbers alone does not establish that all seed requirements have been satisfied.

## 6. Relationship with the Control Tower

Sprint 2 establishes the external integration layer but does not, by itself, complete the end-to-end shipment visibility pipeline.

The intended flow is:

1. A carrier simulator exposes shipment information.
2. The integration service requests shipment data using the carrier-specific contract.
3. The response is validated and parsed.
4. Carrier identifiers and status values are mapped to the internal data model.
5. Business rules determine whether an event can update the shipment's canonical state.
6. Valid events are persisted and made available to the Control Tower.

The simulator and API work supports the first step and parts of the second. The full ingestion, normalization, state-transition enforcement, and end-to-end visibility flow must be tracked separately according to their actual implementation status.

## 7. Validation and acceptance focus

The following checks define the evidence needed to close the sprint's integration work.

| Area | Validation |
|---|---|
| Service startup | Each simulator starts with its required configuration and dependencies. |
| Database connectivity | Each service can access its configured database. |
| Successful lookup | A known tracking number returns the expected shipment data. |
| Unknown shipment | A nonexistent tracking number produces the documented response. |
| Error handling | Supported failure scenarios return the expected HTTP status and response body. |
| Rate limiting | Requests exceeding the agreed limit are handled according to the contract. |
| Seed reproducibility | Seed execution produces the expected dataset. |
| Seed idempotency | Repeated seed execution does not introduce unintended duplicates. |
| Carrier differences | Status values and date formats remain faithful to their respective carrier contracts. |
| Documentation | Each endpoint, configuration requirement, and test procedure is documented. |

A validation item should be marked complete only when supported by code, a reproducible test, or other verifiable evidence.

The Sprint 2 work provides the following foundations for subsequent development:

- Carrier simulator services for integration testing.
- A Type B REST pull contract based on shipment tracking numbers.
- A heterogeneous persistence design for the four Type B services.
- Configurable failure scenarios for API testing.
- Seed-data and reproducibility requirements.
- A defined integration boundary between carrier-specific data and the Control Tower's canonical model.
- Validation criteria for progressing toward ingestion and end-to-end shipment visibility.

The final sprint handoff should include the current repository structure, Docker Compose configuration, environment setup, seed execution instructions, endpoint examples, and test results. Any unverified implementation item should remain open rather than being reported as completed.

## 9. Completed implementation achievements

The core Control Tower ingestion pipeline and asynchronous architecture were fully implemented, tested, and merged into `develop`:

1. **HU-20 — Webhook Ingestion & RN-02 Protection**: Decoders for all 5 Type A carrier formats (flat JSON, nested JSON with numeric codes, Spanish JSON, XML, URL-encoded form), canonical status mapping via `state_mapping_cache`, terminal state protection (**RN-02**), and anomaly tracking in `tracking_anomalies`.
2. **HU-21 — Type B Carrier REST API Connector**: `TypeBConnectorService` polling tracking endpoints with exponential backoff on HTTP `429 Too Many Requests` and `5xx` server errors, standardizing timestamp formats, and normalizing to canonical statuses.
3. **HU-22 — Type C Batch File Connector**: `TypeCConnectorService` ingesting CSV and XLSX files, stripping Defect 5.3 total/summary rows and repeated headers mid-file, and guaranteeing idempotency via SHA-256 hash deduplication in `processed_files`.
4. **HU-23 — RabbitMQ Webhook Decoupling (RNF-01)**: Fully decoupled webhook ingestion with a Topic Exchange (`eventos_exchange`), durable main queue (`eventos_transportadora`), retry queue with TTL (`eventos_transportadora.retry`), and dead-letter queue (`eventos_transportadora.dlq`). Achieved **p95 response latency of 32.60 ms** (Target: &le; 200 ms).
5. **HU-24 — Standalone Consumer Worker with ACK/NACK**: Independent background daemon `app.worker` consuming events with fair dispatch (`prefetch_count=10`), sending `ACK` on success, routing transient errors to the retry queue, and routing exhausted retries or malformed messages via `NACK` to the DLQ.
6. **Quality Gate Metrics**: 140 passing automated unit/integration tests with **86.07% code coverage**, full static typing with Mypy, and zero Ruff lint/formatting warnings.

## Sprint outcome

Sprint 2 established the simulator and API foundations needed to integrate multiple carrier systems with different contracts and data representations. The work makes it possible to test carrier lookups and integration failure scenarios in a controlled environment.

The principal outcome is a foundation for the next stage of development: connecting these external services to a reliable ingestion and normalization pipeline that supports consistent shipment visibility in the CargaExpress Control Tower.
